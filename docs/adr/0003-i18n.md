# Internationalization without an i18n framework in the browser apps

## Context and Problem Statement

Every front end had hardcoded English copy. How do the apps get a second
language while staying lightweight, and how does a visitor's choice carry
across `*.gtfs.zone` subdomains?

## Decision Drivers

- No runtime dependency and no translation platform
- One choice of language for every gtfs.zone app
- The homepage and sites must read with JavaScript off

## Considered Options

- i18next or FormatJS in every app
- A hand-rolled typed `t()` in web-common
- Gettext catalogs

## Decision Outcome

Chosen option: a hand-rolled typed `t()` in web-common for the browser
apps, gettext for timetable-sites.

- **Browser apps.** web-common's `src/i18n` defines a catalog from the
  English strings; `t()` accepts only its keys, and every other locale is a
  partial translation that falls back to English. `{var}` placeholders,
  plurals by `_one` / `_other` suffixes picked with `Intl.PluralRules`.
  Dates and numbers go through the shared `fmt` helpers over `Intl`.
  Catalogs are plain objects, so a later move to i18next or FormatJS only
  replaces the helper.
- **Locales.** `en` (source), `fr`, `de`. A new string goes in all three.
- **Selection.** A `locale` cookie on `Domain=.gtfs.zone` (localStorage is
  per subdomain), localStorage on localhost, then `navigator.language`,
  then `en`. No locale in app URLs.
- **Homepage.** Built once per locale (`/`, `/fr/`, `/de/`, plus regional
  `/fr-ca/` and `/de-ch/`), with `hreflang` alternates; the toggle navigates
  between them.
- **timetable-sites.** Python and Jinja, so gettext `.po` catalogs per
  locale with Babel for dates and lists; the locale is set per site in
  `sites.yaml`, with no toggle.
- **Never translated:** GTFS field names, file names and enum values.
- **Translations** are drafted by Claude and reviewed in the PR.

### Consequences

- Good, because the apps add no dependency and the key set is type-checked.
- Good, because one cookie sets the language on every subdomain.
- Bad, because there is no translation memory or platform for outside
  translators.
- Bad, because sites and the browser apps use two catalog formats.
